# ItemSplit 공통 API 및 DB 계약

작성일: 2026-09-30

버전: 1.1

상태: 확정

이 문서는 A·B가 함께 사용하는 데이터 의미, 저장·검증·정산 동작 및 API·DB 계약을 정의한다. 공통 기반의 적용 대상은 기존 영수증·품목·참여자·정산 기능이다. 이미지·OCR 항목은 연결 시 지켜야 할 경계 계약이며 S3·OCR 구현 완료를 의미하지 않는다.

## 1. 공통 데이터 의미

다음 규칙을 A·B 공통 기준으로 적용한다.

| 필드·개념 | 확정 기준 |
|---|---|
| `userId` | 로그인 계정인 `User.id`. 방 참여자 ID와 교환해서 사용하지 않는다. |
| `memberId` | 해당 방의 `RoomMember.id`. 수동 멤버도 같은 기준을 사용한다. |
| `payerMemberId` | 영수증을 결제한 해당 방의 `RoomMember.id`. 미지정은 `null`이다. |
| `memberIds` | 해당 품목에 참여하는 방 멤버 ID 목록. 중복 ID는 한 번만 적용하고, 빈 배열만으로 정산 제외를 뜻하지 않는다. 별도의 명시적 제외 상태가 없으면 참여자 미지정이다. |
| `receiptId`·`itemId` | 서버가 발급한 영수증·품목 ID. 수정 시 기존 ID를 유지하고, 다른 방·영수증의 ID를 섞지 않는다. |
| `price` | 품목 한 개의 단가. 행 전체 금액으로 해석하지 않는다. |
| `quantity` | 품목 수량. 정산에 반영할 때는 양의 정수여야 한다. |
| 품목 금액 | `price × quantity`. 서버가 계산하며, 클라이언트 계산은 미리보기다. |
| `declaredTotal` | 영수증 원본 또는 사용자가 별도로 확인한 총액. 초안에서는 `null` 허용, 송금 정산 전에는 입력·확정해야 한다. 품목 합계로 자동 덮어쓰지 않는다. |
| `purchasedAt` | 거래 날짜. 현재와 같은 `YYYY-MM-DD` 형식을 사용한다. 등록 시각인 `createdAt`과 구분한다. |
| `burden`·`paid`·`net` | 각각 부담액·결제액·순정산액. `net = paid - burden`, 양수는 받을 금액, 음수는 보낼 금액이다. |

`payerMemberId`는 먼저 결제한 사람이고, 품목의 `memberIds`는 비용을 부담할 사람들이다. 두 필드를 합치거나 동일한 값으로 강제하지 않는다. 결제자가 특정 품목의 참여자에 포함되지 않아도 된다. DB의 결제자 관계와 품목 참여자 관계도 각각 유지한다. `RoomMember.id`로 통일한다는 것은 두 관계의 역할이 아니라 참조하는 ID의 종류를 통일한다는 뜻이다.

예를 들어 A의 `RoomMember.id`가 `12`, B가 `15`이고 A가 20,000원을 결제한 품목을 함께 부담하면, 영수증의 `payerMemberId`는 `12`, 해당 품목의 `memberIds`는 `[12, 15]`다. A와 B의 부담액은 각각 10,000원이며 B가 A에게 10,000원을 보낸다.

잘못된 멤버 ID는 다른 종류의 ID로 재해석하지 않고 요청 오류로 처리한다. 같은 숫자가 `User.id`와 `RoomMember.id`에 모두 존재해도 필드의 의미에 따라 처리한다. 참여자 API의 `User.id` 재해석 처리는 제거하며, 전환 시 기존 테스트·호출부도 함께 변경한다. 이번 공통 범위에는 사용자 ID를 받는 별도 호환 API를 추가하지 않는다. 모든 결제자·참여자는 요청 대상 방에 속해야 한다.

## 2. 금액과 검증 기준

금액·수량 상한은 식사·회식·여행 등 일반적인 공동 지출을 대상으로 다음과 같이 정한다. 아래 수치는 업계 표준이 아니라 이 서비스의 초기 운영 정책이며, 실제 사용 결과에 따라 계약과 검증을 함께 변경할 수 있다. 모든 경계값은 포함한다.

| 항목 | 허용 범위 | 적용 기준 |
|---|---|---|
| 품목 단가 `price` | 1 ~ 1,000,000원 | 품목 한 개의 금액 |
| 품목 수량 `quantity` | 1 ~ 999개 | 정수만 허용 |
| 품목 금액 | 1 ~ 10,000,000원 | 단가·수량이 각각 유효해도 곱셈 결과를 별도로 검사 |
| 영수증 총액 `declaredTotal` | 1 ~ 10,000,000원 | 초안에서는 미입력을 뜻하는 `null` 허용 |
| 영수증 전체 품목 합계 | 최대 10,000,000원 | 정산 제외 품목까지 포함한 합계 |
| 방 전체 품목 합계 | 최대 100,000,000원 | 방에 저장한 모든 영수증의 품목 금액 합계. 제외 품목도 포함 |

단가는 개인별 부담액이 아니라 실제 한 품목의 가격이므로 100만 원까지 허용하고, 여러 품목이 있는 단체 지출은 영수증당 1천만 원, 여러 영수증을 모으는 여행·모임은 방당 1억 원까지 허용한다. 수량은 999개로 제한해 OCR이 긴 숫자를 수량으로 잘못 읽은 경우를 걸러낸다.

정상 품목 데이터의 생성·수정·OCR 확정 시 위 범위를 검사한다. OCR 원문에 범위를 벗어나는 숫자가 있으면 검토용 초안에 오류로 표시할 수 있지만 정상 품목으로 저장·확정하지 않는다. 범위 내 값이지만 총액이 불일치하는 경우는 초안 저장을 허용하고 정산만 차단한다.

- 통화는 원화이며 소수점 없는 정수로 처리한다. 순정산액을 제외한 정상 단가·금액에는 음수를 허용하지 않는다.
- 정산 가능한 일반 품목은 단가와 수량이 모두 양수여야 한다. 무료 품목·할인·환불을 일반 품목에 임의로 섞어 처리하지 않는다.
- 단가·총액 등 저장 금액 필드는 Java `long` 및 PostgreSQL `BIGINT`를 사용하고, 곱셈·합산·정산 계산도 `long`으로 처리한다. 값이 없을 수 있는 총액에는 Java `Long`과 DB의 nullable 컬럼을 사용한다. 수량은 정수와 별도 상한으로 관리한다.
- JSON 금액을 프론트엔드 `number`로 처리할 수 있도록 개별 금액뿐 아니라 곱셈·영수증 합계·방 합계도 안전한 정수 범위 안으로 제한한다. 업무용 상한은 위 표를 사용한다. 정산 제외로 저장 상한을 우회할 수 없다.
- 서버에서 단가·수량·곱셈 결과·합계의 허용 범위를 검사한다. 합산 후 넘친 값을 검사하는 방식에 의존하지 않는다. 수정 시 기존 금액을 새 금액으로 교체한 결과를 검사하고, 같은 방의 동시 저장으로 방 합계 상한이 초과되지 않도록 한다. 초과 요청은 해당 저장 전체를 거부하고 HTTP 400 `VALIDATION_ERROR`를 반환한다.
- 원본 총액과 품목 합계는 별도로 유지하고 차이를 표시한다. 합계를 맞추기 위해 OCR 값이나 사용자 입력을 자동 변경하지 않는다.

DTO·엔티티·DB의 금액 타입은 위 기준을 공유한다. 화면은 `number`를 사용하고 정수 및 공통 상한 검증을 동일하게 적용한다. JSON의 소수 금액·수량을 정수로 잘라서 받지 않는다.

## 3. 저장과 정산 규칙

| 상황 | 확정 기준 |
|---|---|
| 이름·날짜·결제자 수정 | 기존 품목별 참여자 배정을 보존한다. |
| 품목 가격·수량 수정 | 해당 품목의 참여자는 보존하고 금액만 다시 계산한다. |
| 참여자 일괄 지정 | 사용자가 명시적으로 일괄 적용을 선택했을 때만 수행한다. |
| 영수증 전체 저장 | 영수증·품목·배정을 하나의 DB 트랜잭션으로 처리한다. 일부 검증이 실패하면 전체 변경을 취소한다. |
| 재시도·중복 제출 | 수기 생성은 `requestId`로 같은 작업을 식별한다. 같은 식별자·같은 요청의 재전송은 기존 영수증을 반환하고, 같은 식별자·다른 요청은 거부한다. OCR 확정도 동일 작업의 중복 반영을 허용하지 않는다. |
| 결제자 미지정 | 초안 저장은 허용한다. 정산 대상 금액이 있는 영수증은 송금 정산 전에 결제자를 지정해야 한다. |
| 참여자 미지정 | 명시적으로 제외하지 않은 품목은 참여자를 지정할 때까지 송금 정산을 차단한다. 자동 배정·자동 제외하지 않는다. |
| 명시적 정산 제외 | 사용자가 선택한 품목만 부담액·결제액 계산에서 함께 제외한다. 품목과 금액은 보존하며 원본 총액 검증에는 포함한다. |
| 총액 불일치 | 초안 저장은 허용하되, 원본 총액과 전체 품목 합계가 정확히 일치할 때까지 송금 정산을 차단한다. 단순 확인으로 우회할 수 없다. |
| OCR 미확정 | 검토용 초안으로 유지하고 사용자가 확정하기 전에는 정산 품목에 포함하지 않는다. |
| 정상 정산 | 정산에 포함된 품목에 대해 `sum(paid) == sum(burden)` 및 `sum(net) == 0`을 보장한다. |
| 나머지 금액 | 동일한 품목·금액·참여자 집합이면 조회 및 재저장 순서에 관계없이 같은 결과를 낸다. |
| 정산 준비 미완료 | 누락 사유를 제공한다. 입력이 불완전한 상황을 “송금할 내역 없음”으로 표시하지 않는다. |

정산 준비 상태는 현재 영수증·품목·배정을 조회해 계산한다. 미완성 입력은 초안으로 저장할 수 있지만 송금 결과를 제공하지 않는다. 품목의 명시적 제외는 `excludedFromSettlement`로 저장하며 기본값은 `false`다.

영수증 전체 저장은 완전한 품목 목록을 받는다. 기존 품목 ID가 목록에서 빠지면 해당 품목과 배정을 삭제한다. 기존 ID가 있으면 유지·수정하고, `itemId = null`이면 신규 품목을 생성한다. 필수 목록 생략이나 `null`을 유지 요청으로 해석하지 않는다. 메타정보만 수정하는 API는 품목·배정에 영향을 주지 않는다.

## 4. 이미지와 OCR 데이터 기준

- 이미지 원본은 저장소에 보관하고 DB에는 객체 키·파일 형식·크기 등 메타데이터를 저장한다. 기한이 있는 조회 URL을 영구 식별자로 저장하지 않는다.
- 이미지 저장·조회·삭제는 방 접근 권한을 기준으로 처리한다. 공유 토큰이 있다고 원본 이미지 조회까지 자동 허용하지 않는다.
- 영수증·방 삭제 시 원본 파일 정리도 포함한다. DB와 파일 저장소 간 실패는 재시도·보상 처리로 정리하며, DB 트랜잭션이 파일 작업까지 되돌린다고 가정하지 않는다.
- OCR 결과는 단가·행 금액·수량·총액을 구분한다. 없는 값이나 불확실한 값을 임의의 정상값으로 채우지 않고 검토 대상으로 남긴다.
- OCR 재시도가 사용자 수정 내용이나 이미 확정한 품목을 자동으로 덮어쓰지 않게 한다.
- OCR 공급자 고유 응답과 프로젝트 내부 데이터를 분리한다. 내부 데이터에는 누락·불확실성·검토 사유를 보존하며, 공급자 응답을 기존 품목 테이블에 직접 저장하지 않는다.

## 5. 정산 정책

명시적 정산 제외는 허용하고, 총액 불일치는 해결한 뒤 정산한다. 다음 규칙을 초기 서비스의 공통 정산 기준으로 적용한다.

### 명시적 정산 제외 허용

- 참여자 미지정과 정산 제외를 구분한다. API 필드는 `excludedFromSettlement`, DB 컬럼은 `items.excluded_from_settlement`다.
- 기본은 정산 대상이며, 사용자가 ‘정산 제외’를 선택해야 제외된다. 제외된 품목은 화면에 표시하고 다시 포함할 수 있게 한다.
- 제외 상태의 품목에는 참여자를 저장하지 않는다. 화면에서 기존 배정을 해제할 결과를 안내하고 제외 상태와 배정 해제를 한 번에 저장한다. 제외와 참여자 배정이 동시에 전달되면 서버는 오류로 처리한다.
- 다시 포함하면 참여자를 지정해야 한다. 지정 전에는 검토 필요 상태이며 정산을 진행하지 않는다.
- 제외 품목은 참여자의 부담액과 결제자의 정산 대상 결제액 양쪽에서 제외한다. `paid`는 이때 원본 영수증 전체 결제액이 아니라 정산에 포함한 품목의 결제액이다.
- 개인 구매라도 다른 사람이 대신 결제했고 아직 갚지 않았다면 본인 한 명을 참여자로 지정한다. 제외는 이번 정산에서 처리하지 않을 지출에 사용한다.

### 총액 불일치 해결 후 정산

- 비교 대상은 `declaredTotal`과 **제외 품목까지 포함한 전체 품목 합계**다. 정산 대상 금액이 원본 총액보다 작은 것은 명시적 제외에 따른 정상 동작일 수 있다.
- 원 단위 오차 허용 없이 두 값이 같아야 한다. 1원이라도 다르면 차이와 대상 영수증을 표시하고, 방의 송금 정산 결과 제공·확정·공유를 차단한다. 초안 저장과 오류 확인은 가능하다.
- 참여자가 빠진 품목을 제외하거나 확인 버튼을 누르는 방식으로 총액 차이를 무시할 수 없다.
- 초안의 `declaredTotal = null`은 비교 완료가 아니다. 송금 정산 전에 값을 입력·확정한다. 이미지 영수증은 원본에서 확인하며, 수동 등록은 사용자가 실제 결제 총액을 입력하거나 표시된 품목 합계를 확인해 명시적으로 총액으로 확정한다. 품목 수정 후 자동으로 총액을 맞추지 않는다.
- OCR 오인식·누락·중복을 수정하고 할인·추가 비용을 실제 결제 내역에 맞게 반영한 뒤 정산한다. 일반 품목은 실제 결제된 단가·수량을 사용한다. 차액을 임의로 생성하거나 배분하지 않는다.
- 모든 품목이 제외된 영수증도 입력 총액과 전체 품목 합계는 검증한다. 일치하고 방 전체의 정산 대상 품목이 없으면 ‘정산 대상 없음’으로 안내하며 송금 목록은 비워 둔다. 이 경우 제외된 지출의 결제자 지정을 요구하지 않는다.

### 정책 확인 예시

| 상황 | 기대 동작 |
|---|---|
| 단가 1,000,000원·수량 10개 | 품목 금액 10,000,000원으로 허용. 영수증·방 합계 조건도 충족해야 함 |
| 단가 1,000,001원 또는 수량 1,000개 | 정상 품목 저장 거부 |
| 단가 1,000,000원·수량 11개 | 개별 입력은 범위 안이지만 품목 금액 상한 초과로 저장 거부 |
| 영수증 합계 10,000,001원 또는 방 합계 100,000,001원 | 상한 초과로 해당 저장 전체 거부 |
| 총액 34,000원·전체 품목 34,000원·명시적 제외 10,000원 | 총액 검증 통과. 나머지 정산 조건 충족 시 24,000원 정산 |
| 총액 34,000원·전체 품목 34,000원·참여자 없는 품목 10,000원 | 명시적 제외가 아니므로 정산 차단 |
| 총액 30,000원·전체 품목 33,000원 | 초안 저장 가능, 3,000원 차이를 해결하기 전 정산 차단 |
| 총액 30,000원·전체 품목 33,000원·명시적 제외 3,000원 | 전체 품목 합계는 여전히 33,000원이므로 정산 차단 |
| 총액 미입력·품목 합계 30,000원 | 초안 저장 가능, 총액 입력·확정 전 정산 차단 |

## 6. 기존 기능의 API 계약

모든 인증 API는 해당 방에 대한 멤버 권한을 확인한다. 응답은 기존 `success`, `data`, `error` 포맷을 유지한다. 잘못된 입력·ID 종류·정산 조건은 HTTP 400 `VALIDATION_ERROR`, 다른 방에 속한 영수증 등 없는 대상은 HTTP 404 `NOT_FOUND`, 방 접근 권한이 없으면 HTTP 403 `FORBIDDEN`이다.

### 영수증 조회와 저장

| 메서드·경로 | 계약 |
|---|---|
| `GET /api/rooms/{roomId}/receipts` | 영수증 요약 목록 |
| `GET /api/rooms/{roomId}/receipts/{receiptId}` | 요약 필드, 품목별 `memberIds`·`excludedFromSettlement`, 총액 차이 `warning` |
| `POST /api/rooms/{roomId}/receipts/manual` | 생성 식별자와 메타정보·품목·참여자를 한 트랜잭션으로 생성. 재시도 포함 HTTP 201, 상세 응답 |
| `PUT /api/rooms/{roomId}/receipts/{receiptId}` | 이름·결제자·입력 총액·날짜만 수정. 품목·배정·제외 상태는 보존 |
| `PUT /api/rooms/{roomId}/receipts/{receiptId}/contents` | 메타정보와 완전한 품목 목록을 한 트랜잭션으로 교체. HTTP 200, 상세 응답 |
| `DELETE /api/rooms/{roomId}/receipts/{receiptId}` | 영수증·품목·배정 삭제, DB 커밋 후 로컬 원본 파일 정리. HTTP 204 |

수기 생성 요청 예시:

```json
{
  "requestId": "68173204-84c0-41c3-bff7-0c63e3671d24",
  "name": "저녁 식사",
  "payerMemberId": 12,
  "declaredTotal": 20000,
  "purchasedAt": "2026-09-30",
  "items": [
    {
      "itemId": null,
      "name": "음식",
      "price": 10000,
      "quantity": 2,
      "memberIds": [12, 15],
      "excludedFromSettlement": false
    }
  ]
}
```

- `requestId`: 수기 생성에서 필수인 1~64자 식별자. 화면은 UUID를 생성해 같은 요청의 네트워크 재시도에 재사용한다. 내용이 바뀌면 새 식별자를 사용한다. 방별로 유일하며 요청 내용의 해시를 함께 보관한다. 같은 요청이 다시 도착하면 기존 영수증의 현재 상세를 반환한다.
- `name`: 공백 제외 1~100자. 서버에서 앞뒤 공백을 제거한다.
- `payerMemberId`, `declaredTotal`, `purchasedAt`: 생략 또는 `null`이면 미지정이다. PUT에서도 이전 값 유지가 아니라 미지정으로 저장된다.
- `items`: 필수이며 하나 이상의 품목을 포함한다. 목록·원소의 `null`은 허용하지 않는다. 빈 영수증을 만들기 위해 이 요청을 사용하지 않는다.
- `itemId`: 생성에서는 생략 또는 `null`만 허용한다. 전체 수정에서는 기존 ID 또는 신규를 뜻하는 `null`을 사용한다. 중복 ID·다른 영수증 ID는 거부한다.
- 품목의 `memberIds`와 `excludedFromSettlement`는 필수이며 `null`을 허용하지 않는다. `memberIds = []`는 배정 없음, `excludedFromSettlement = true`는 명시적 제외다. 제외와 비어 있지 않은 참여자 목록은 함께 저장할 수 없다.
- 전체 수정 요청은 위 예시에서 `requestId`를 제외한 형식이다. 명시적 제외를 선택하면 화면이 배정 해제를 안내하고 빈 `memberIds`와 함께 저장한다.
- 금액·멤버·품목 ID 중 하나라도 유효하지 않으면 영수증·품목·배정을 모두 변경하지 않는다. 원본 총액 불일치 자체는 초안 저장을 막지 않는다.

### 개별 품목과 참여자

기존 품목 생성·수정·삭제 및 `PUT .../items/{itemId}/assignees`는 유지하며 같은 금액 상한·방 권한·멤버 ID 규칙을 적용한다. 가격·수량 수정은 참여자와 제외 상태를 보존한다. 개별 참여자 API는 제외 품목에 비어 있지 않은 배정을 허용하지 않는다. 제외 상태 변경은 영수증 전체 저장으로 처리한다.

### 정산 및 공유

`GET /api/rooms/{roomId}/settlements`는 HTTP 200의 `data`에 다음 구조를 반환한다.

```json
{
  "roomId": 1,
  "roomName": "모임",
  "ready": false,
  "members": [],
  "issues": [
    {
      "code": "MISSING_ASSIGNEES",
      "receiptId": 21,
      "itemId": 31,
      "message": "참여자를 지정하거나 명시적으로 정산에서 제외해 주세요."
    }
  ]
}
```

- `ready = false`: 송금 계산용 `members`는 빈 배열이며 `issues`에 차단 사유를 반환한다. 화면은 이를 정상적인 ‘송금 내역 없음’으로 표시하지 않는다.
- `ready = true`: `issues = []`이며 `members`는 기존 `memberId`, `userId`, `nickname`, `linked`, `burden`, `paid`, `net` 구조다. 영수증이 없거나 검증을 통과한 모든 품목이 제외되어 있으면 각 멤버의 금액은 0이다.
- 차단 코드: `MISSING_DECLARED_TOTAL`, `TOTAL_MISMATCH`, `MISSING_PAYER`, `MISSING_ASSIGNEES`, `EMPTY_RECEIPT`, `INVALID_ITEM_AMOUNT`, `INVALID_DECLARED_TOTAL`, `RECEIPT_TOTAL_LIMIT`, `ROOM_TOTAL_LIMIT`, `INVALID_PAYER`, `INVALID_ASSIGNEES`.
- 영수증 단위 사유의 `itemId`는 `null`이다. 범위를 벗어나는 기존 저장 데이터도 유효한 정산으로 취급하지 않는다.
- 나머지 배분은 방 멤버 ID 오름차순으로 정렬한 뒤 방·품목 ID 기반의 고정 시드로 순서를 결정한다. 배정 레코드를 재생성해도 같은 참여자 집합의 결과는 같다.
- 공유 토큰 발급 및 기존 토큰을 통한 정산 조회 모두 현재 정산 조건을 다시 확인한다. 미완성 상태이면 HTTP 400 `VALIDATION_ERROR`로 차단한다. 정상 공유 응답은 기존 읽기 전용 응답 형식을 유지한다.

## 7. DB와 일관성 계약

| 대상 | 타입·제약 |
|---|---|
| `items.price` | `BIGINT NOT NULL`, 정상 입력은 1~1,000,000 |
| `items.quantity` | 정수, 정상 입력은 1~999 |
| `items.excluded_from_settlement` | `BOOLEAN NOT NULL DEFAULT FALSE` |
| `receipts.declared_total` | nullable `BIGINT`, 정상 입력은 1~10,000,000 |
| `receipts.payer_member_id` | nullable `RoomMember` 외래 키 |
| `assignments.room_member_id` | 품목 비용을 부담하는 `RoomMember` 외래 키 |
| `receipts.request_id` | nullable `VARCHAR(64)`, 신규 수기 생성 API에서는 필수, 기존·이미지 영수증은 `null` 허용 |
| `receipts.request_fingerprint` | nullable `VARCHAR(64)`, 수기 생성 요청의 SHA-256 |
| `(receipts.room_id, receipts.request_id)` | 유일성 제약 |

품목·영수증 저장은 같은 방의 DB 행 잠금을 잡은 상태에서 합계 검증과 변경을 수행한다. 생성 식별자 확인도 같은 잠금 안에서 수행한다. 동시 요청이 같은 과거 합계를 읽고 각각 상한을 넘겨 저장하거나 같은 요청을 중복 생성하지 않도록 한다. 배정 교체 및 멤버·방 삭제도 저장과 충돌하지 않도록 같은 방의 변경을 직렬화한다. 정산 조회는 `REPEATABLE_READ` 트랜잭션으로 영수증·품목·참여자를 같은 시점의 데이터에서 읽는다. 공유 토큰 발급은 방 잠금 안에서 정산 가능 여부를 확인한다.

기존 데이터의 ID·결제자·참여자·총액은 추측해서 바꾸지 않는다. 기존 미배정 품목의 제외 기본값은 `false`이며 정산 검증에서 수정 필요로 표시한다. 기존 DB용 변경 스크립트는 `db/migrations/001_common_contract.sql`, 데이터 점검은 `db/migrations/001_common_contract_audit.sql`이다. 기존 DB는 로컬·운영 모두 앱 중지와 백업 후 변경 SQL을 먼저 적용한다. 스크립트는 Hibernate의 부분 적용 상태 및 재실행을 지원하며, 기존 제외 값은 유지하고 `NULL`만 `false`로 보정한다. 빈 DB의 테이블 생성은 Hibernate가 담당한다. 로컬 자동 스키마 갱신은 변경 SQL을 대체하지 않으며, 갱신 실패 시 앱 시작을 중단한다. 실행 절차는 `README.md`의 기존 DB 변경 적용을 따른다.

로컬 파일 정리는 DB 트랜잭션 결과에 따른다. 삭제가 커밋되면 원본 파일을 지우고, 업로드 DB 저장이 롤백되면 새 파일을 지운다. 부분 업로드 파일의 즉시 삭제 실패도 정리 대상에 포함한다. 실패한 삭제는 저장 루트의 `.cleanup-pending`에 기록하고 앱 시작 및 60초 간격으로 재시도한다. 프로세스 강제 종료로 콜백이 실행되지 않은 구간과 정리 기록 자체를 저장할 수 없는 장애까지 원자적으로 보장하지는 않는다.

## 8. 공통 수용 기준

- 결제자·참여자 역할과 수동 멤버를 보존하고 `RoomMember.id`만 해석한다.
- 메타정보·가격 수정으로 품목별 참여자가 바뀌지 않는다.
- 실패한 통합 저장의 부분 변경과 같은 생성 요청의 중복 영수증이 남지 않는다.
- 금액 상한은 제외 품목을 포함하며 동시 저장으로 우회할 수 없다.
- 제외는 결제액·부담액 양쪽에서 빠지고 원본 총액 검증에는 남는다.
- 누락·불일치 상태는 사유와 함께 정산·공유를 차단한다.
- 정상 정산의 `sum(paid) == sum(burden)`, `sum(net) == 0`과 배정 순서에 독립적인 나머지 분배를 보장한다.
- 기존 수정·삭제 권한은 유지한다. 현재 완료·확정본 기록은 이 계약의 API에 포함하지 않는다.
