# 보존된 로컬 OCR E2E 환경

기존 테스트 계정, 방, 참여자, 업로드 사진, 실제 CLOVA 인식 결과와 반영된 정산 품목을 재사용한다. 실행할 때 계정·방·영수증을 새로 만들거나 OCR을 호출하지 않는다.

## 바로 실행

Docker를 켜고 프로젝트 루트에서 실행한다. Java 21, Node.js/npm, Python 3가 필요하다. macOS에서는 설치된 Java 21을 자동 선택한다. 다른 환경은 `JAVA_HOME`으로 지정한다. 실제 OCR 설정은 기존 `.env`의 `CLOVA_OCR_INVOKE_URL`, `CLOVA_OCR_SECRET`을 사용한다.

```sh
./scripts/e2e.sh up       # 기존 DB 시작, 현재 코드 빌드, 백엔드·웹 실행, 데이터 검사
./scripts/e2e.sh test     # 기존 계정으로 자동 로그인한 브라우저 + UI 검증
./scripts/e2e.sh test-items # 수동 품목 추가·참여자·정산 검증 후 이번 테스트 품목만 삭제
```

웹 주소는 <http://127.0.0.1:5173>이다. 백엔드는 `127.0.0.1:18080`, DB는 `127.0.0.1:15432`를 사용한다. 자동 검증은 `itemsplit-e2e-tests` 세션에서 실행하고 종료 시 닫는다. 직접 사용하는 `itemsplit-preserved` 세션은 `browser.config.json`의 `viewport: null`로 새로 열어 실제 Chrome 창 크기를 따른다. 로그인 응답을 보호된 로컬 브라우저 상태 파일로 로드하여 인증을 우회하지 않고 로그인 폼 입력을 생략한다. 이메일·비밀번호는 `.local/e2e/fixture.json`에서 확인할 수 있다.

반응형 검사에 사용한 1440×1080 강제 뷰포트를 사용자 창에 남겨두면 실제 창보다 페이지가 커져, 스크롤 끝의 저장 버튼이 잘릴 수 있다. CSS 내부 스크롤 문제와 구분해야 한다. `./scripts/e2e.sh open`은 검증 없이 실제 창 크기의 화면만 다시 연다. 미저장 폼 입력은 새 창에 복원되지 않으며 DB·로그인 계정·기존 테스트 데이터는 그대로 사용한다.

`up`은 자신이 시작한 서버만 재시작한다. 다른 프로세스가 포트를 사용하면 자동으로 종료하지 않고 충돌을 알린다. 상태가 예상과 달라도 데이터를 초기화하지 않는다.

```sh
./scripts/e2e.sh check    # 계정·참여자·OCR·사진 해시·품목·정산 API 읽기 검증
./scripts/e2e.sh open     # 강제 뷰포트 없는 Chrome 화면 열기
./scripts/e2e.sh status   # DB와 서버 상태
./scripts/e2e.sh backup   # 현재 DB와 사진, 케이스 정보를 별도 시각 폴더에 백업
./scripts/e2e.sh down     # 서버·DB만 종료. 데이터 삭제 없음
```

## 보존 대상

| 대상 | 위치 / 기대 상태 |
|---|---|
| PostgreSQL | 외부 Docker 볼륨 `itemsplit-e2e_itemsplit-postgres-data` |
| 사진 원본 | `.local/e2e/storage/receipts/…` — `gradlew clean` 대상 밖 |
| 계정·케이스 식별자 | `.local/e2e/fixture.json` — 기존 계정, 방 1, 영수증 1, 작업 1 |
| 참여자 | 현재 DB에 저장된 참여자와 배정 유지 |
| OCR | `CLOVA_RECEIPT`, `SUCCEEDED`, 사진 시도 횟수 1, 초안 `APPLIED` |
| 정산 품목 | Beef Soup 8,000원 × 2, Cola 1,000원 × 2 (품목명 검토 수정 포함) |
| 정산 결과 | 현재 모든 영수증의 정산 대상 품목·결제자·참여자 배정으로 계산 (고정 금액 없음) |
| 백업 | `.local/e2e/backups/<실행시각>/database.dump`, `storage.tar.gz`, `fixture.json` |
| 브라우저 캡처 | `.local/e2e/screens/receipt-review.png`, `receipt-mobile.png`, `settlement.png` |
| 실행 로그·PID | `.local/e2e/backend.log`, `frontend.log`, 각 `.pid` |
| 로컬 URL 서명 키 | `.local/e2e/image-signing.key` — JWT 키와 별도로 생성·보존 |

`.local/` 전체는 Git 및 Docker 빌드 컨텍스트에서 제외한다. 계정 정보·로그인 토큰·서명 키·DB 덤프를 커밋하지 않는다. 이 환경은 현재 머신에 보존한 케이스를 사용하므로 새로운 checkout만으로 데이터가 생성되지는 않는다. 다른 머신으로 옮길 때는 해당 백업과 기존 환경 설정이 필요하다.

종료 명령은 `compose stop`을 사용한다. 외부 볼륨은 Compose의 일반 삭제 대상도 아니다. 직접 `docker volume rm`이나 `.local/e2e` 삭제를 하면 보존 데이터가 없어지므로, 환경 정리가 필요할 때는 먼저 `backup`을 실행한다. 백업 복구는 DB와 사진을 함께 복구해야 한다. 실행 스크립트에는 기존 DB를 덮어쓰는 자동 복구·초기화 명령을 두지 않았다.

## 테스트 범위와 호출 제한

- `check`: 로그인만 POST하고, 나머지는 GET으로 읽는다. 원본 파일의 SHA-256과 OCR 시도 횟수도 검증한다.
- 배치·스크롤 검사: 1440×800, 1024×700, 390×700에서 멤버 → 목록 → 편집 순서, 사진 첨부 기본 선택, 입력 방식 전환 및 값 유지, 지연된 목록 갱신 중 새 작성 유지를 확인한다. 긴 수동 입력 폼과 기존 영수증의 수동 추가 폼에서 실제 휠 입력으로 저장 버튼에 도달하고 좌표로 클릭한다. 이 검사는 폼 제출만 포착해 데이터 저장을 막는다.
- 실제 창 검사: 자동 검증용 창을 닫고 강제 뷰포트 없는 Chrome에서 OS 창 자체를 1100×800, 900×650으로 바꾼다. 실제 콘텐츠 높이가 창 전체보다 작은지, 휠로 두 저장 버튼에 도달하고 클릭할 수 있는지 검사한다. 검사 후 원래 창 크기로 복원하며 `viewport: null`을 유지한다.
- 원본·정산 검사: 실제 보존 DB를 사용해 원본 표시, 확대·축소, 품목 출처·좌표, 모바일 전환, 새로고침, 정산 화면을 검증한다. GET 외 API 요청은 차단한다.
- 초안 입력 검사: 같은 GET 응답을 브라우저에서만 편집 중 상태·URL 만료 상태로 바꿔, 이미지 갱신과 모바일 탭 전환에서 미저장 입력이 유지되는지 확인한다. 서버의 `APPLIED` 상태와 품목은 수정하지 않는다.
- `test-items`: `+`로 새 영수증 작성 시 빈 상세 패널이 없는지, 기존 영수증을 다시 선택할 수 있는지 검사한다. 반영된 영수증에서 `누락 품목 추가`를 눌러 임시 품목 1,500원 × 2를 실제 저장하고 현재 참여자들을 지정한다. 재접속·모바일 화면·현재 정산액에 추가 품목 금액만큼 반영되는지 확인한 뒤, 성공/실패와 관계없이 이번 테스트가 추가한 품목만 삭제한다. 기존 품목·참여자 배정·OCR 응답·정산 결과가 실행 전과 동일한지 검사한다. 계정·방·영수증·사진·OCR은 새로 만들지 않는다. 기존 데이터를 통째로 초기화하거나 백업으로 덮어쓰지 않는다.
- 브라우저 검사가 실패하면 `test`와 `test-items`도 실패로 종료한다. 다음 브라우저 검증에 필요한 API 요청 여유가 부족하면 자동으로 60초 대기한다. 준비·확인 단계의 API가 429를 반환하면 `Retry-After`에 따라 최대 60초씩 두 번 재시도하며, 서버의 요청 제한은 변경하지 않는다.
- `test-items`의 두 번째 검사는 브라우저 응답만 조작해 저장 중 영수증을 전환해도 현재 선택이 유지되는지, 저장 후 조회가 실패하면 재입력을 유도하지 않고 갱신 실패 안내를 표시하는지 확인한다. 이 단계는 DB를 쓰지 않는다.
- `test` 종료 후 `check`를 다시 실행해 데이터가 그대로인지 확인한다. 고정 합계는 사용하지 않고 모든 영수증의 정산 대상 품목과 참여자 배정으로 결제액·부담액·차액을 검증한다. 나머지 원 단위 배분은 멤버별 허용 범위와 전체 합계를 검증한다. 새 데이터를 생성하거나 기존 데이터를 원복하지 않는다.
- 일반 Java/프론트엔드 테스트는 별도의 임시 DB·합성 응답을 사용한다. 이 보존 DB를 초기화하지 않는다.
- 이 작업의 CLOVA 실제 호출은 누적 2회이며, 사진 조회·환경 보존·반복 E2E 과정의 추가 호출은 0회다. `clovaSmokeTest`는 별도의 실제 유료 호출이므로 이 재사용 테스트에 포함하지 않는다.
